**The methodological requirement first, since it determines everything else.** "Nothing slips through the cracks" means every distinct concept from the DAG design gets exactly one canonical Solvent representation — not "usually represented this way, but sometimes encoded differently depending on which agent wrote it." Any concept with two plausible representations is exactly where meaning gets lost, because two workers will pick differently and neither will be wrong by the letter of the design. So the mapping below is deliberately forced to single answers, and I flag the few places I genuinely can't force a single answer without seeing the actual schema.

**The core mapping.**

| DAG concept | Solvent representation | Why single-valued |
|---|---|---|
| Node (any claim — axiom, definition, result, hypothesis) | One `Belief`, scoped to a `Scenario` | Every claim, regardless of kind, is a belief. No separate "axiom table" vs "theorem table" — that split is exactly the kind of representational fork that causes drift. |
| Epistemic kind (was IST-axiom / hypothesis / established-external-result) | `Belief.claim_type` ∈ {Postulated, Accommodated, Derived} | Solvent already forces this to three values. Map many-to-few explicitly once, in writing, so no worker re-derives the mapping differently: axiom→Postulated, external-cited-result→Accommodated, in-house-proved→Derived. |
| Mathematical/verification state (open / proved / refuted / restricted) | `Belief.status` ∈ {entered, promoted, retracted} **plus** the `Debt` array | "Open" = entered with nonempty debt. "Proved" = promoted (only possible once debt is empty — never a separate flag an agent sets). "Refuted" = retracted. "Restricted" is not a fourth status — see below, it needs its own construction, not a new enum value. |
| The review obligations gating a claim (citation check, adversarial attack, dependency-impact check, human sign-off) | A fixed, named `Debt` vocabulary — enumerated once, generated from one source of truth, never hand-typed per-belief | This is where Solvent's own discipline is instructive: the debt vocabulary is generated directly from the kernel's source enum and the agent-facing tool refuses any debt-item name that isn't in that enum, *before* touching the database. That single mechanism is what prevents "provenance_check" on one node and "citation_check" on another from silently meaning the same thing to a human and different things to the ledger. |
| Supporting artifacts (a proof writeup, a counterexample construction, a numerical check) | `Evidence` rows linked to the `Belief` | Adding evidence never auto-discharges debt — a human or an explicit tool call must still retire the specific debt item. This is the mechanism that prevents "I attached something that looks relevant" from silently counting as "the obligation is met." |
| Downstream work that relies on a claim being currently true | An `Action Intent` citing the `Belief` | The only thing the kernel checks is: does this intent cite a belief that is promoted *right now*. Nothing more. |
| A claim whose truth depends on a narrower set of conditions than the general case | The general Belief gets **retracted** (it's false unstated); a **new**, separately-scoped Belief is entered stating the narrower true claim; linked by a `supersedes`-type edge | This is the one place the DAG design's old "RESTRICTED" status has to be actively re-thought rather than translated — Solvent has no partial-truth state, and inventing one would be exactly the kind of new kernel semantics the domain-blindness rule forbids. Retract-and-supersede reuses machinery that already exists rather than adding a state. |
| A downstream claim wanting to rely on a narrower claim under conditions it needs to verify it actually satisfies | A separate `Belief` — an **attestation** — stating "context X's assumptions fall within claim Y's scope," carrying its own debt, promoted independently, and cited by the Action Intent instead of citing Y directly | This is the fix from two turns ago, restated generically: the kernel only ever checks "is the cited belief promoted." It never checks subset relationships. So the subset check has to become its own belief with its own promotion gate, or the check silently never happens at all. |
| Version revision of an existing claim (its statement gets sharpened or corrected) | Retract the old belief (cascades automatically to anything relying on it) → enter a new belief → link via a `supersedes` edge; old belief remains permanently readable, never deleted | Solves "old version stays citable and immutable" without a parallel version-number field, because retraction is a status flip, not a deletion. |
| "This is stale because something upstream changed" | **Not a stored field at all** — a computed query: any belief whose citation edge points at a currently-retracted belief, with no compensating new citation yet | This is the single biggest place a naive translation would slip: building a `STALE-CANDIDATE` enum column duplicates state that the ledger already implies. A stored field can drift from the truth; a computed query can't. |
| "This needs human review before anyone can rely on it" | The single, generic debt item `semantic_applicability_unresolved` (never domain-renamed) — structurally un-retirable through the agent-facing tool interface, retirable only through the human-facing interface | This is the boundary that actually enforces "AI as assistant, not authority": it's not a convention agents are asked to follow, it's a name the agent-facing tool is coded to refuse. |
| Proof-track and attack-track pairing requirement | Two separate `Evidence` entries (tagged by type: supporting / adversarial), with a debt item that can't be retired until *both* exist | Keeps "did anyone actually try to break this" a structural fact checkable by querying evidence rows, not something that has to be remembered. |
| Separate research sub-programs that shouldn't cross-contaminate assumptions | Separate `Scenario`s | Isolation is structural (retraction cascades never cross scenario boundaries), not a naming convention teams are trusted to respect. |
| Which agent/actor is allowed to do what (propose vs. retire mechanical debt vs. retire human-gated debt vs. promote) | An explicit, enumerated capability table per tool-call, not left implicit | "Workers can call X, the Judge can call Y" has to be a concrete list — e.g., any actor may `enter_belief` and `add_evidence`; only a human-facing interface may retire `semantic_applicability_unresolved`; anyone may *attempt* a promotion call, since the CHECK constraint — not the caller's identity — is what actually decides whether it succeeds. |

**The two failure modes this mapping has to guard against by construction, not by policy:**

1. **Identity drift** — citing the right claim by the wrong version. Solved by the retract-and-supersede pattern above: there is no way to "accidentally" cite a stale version, because the old belief's status visibly flips and any edge still pointing at it is discoverable by the computed staleness query.
2. **Validity-scope drift** — citing the right, current version of a claim, correctly, in a context the claim was never actually shown to cover. This is the harder one, and it's not solved by anything version-related — it's solved only by the attestation-belief pattern, applied every time a downstream intent wants to rely on a restricted (narrower-than-general) claim. If this pattern is skipped even once — if an intent is allowed to cite the narrow belief directly instead of through its attestation — the whole design has a hole exactly where it matters most, since restricted claims are the ones most likely to have their scope revisited later.

**What must never enter the kernel, stated as a negative list, because a positive description invites creative exceptions:** the kernel may never contain code that inspects *what* a claim's assumptions are, *why* a debt item exists, or *whether* one condition logically implies another. It checks identity (which row), currency (is that row's status promoted right now), and structural consequence (does retracting this row require refusing that other row). Anything requiring interpretation of the claim's content — including the subset check above — has to be pushed into its own belief, decided by a human or an attestation process, and then handed to the kernel as a plain fact ("this attestation is promoted") that the kernel can check without understanding.

**One thing I can't responsibly resolve without more information, and I'd rather flag it than guess:** whether `belief_edge` in the actual schema carries a type/label column (distinguishing "depends on" from "supersedes" from "provides attestation for"), or whether it's an untyped edge relation. Everything above assumes typed edges are available or addable without touching kernel semantics — that's very likely true structurally (an edge type is just another column, not new invariant logic), but I haven't verified it against `db/001_schema.sql` directly, and this is exactly the kind of unverified assumption that shouldn't get load-bearing status in a design document. Worth confirming against the actual schema file before this mapping is treated as final.

**A completeness check to run on the design itself, not just once but as a standing audit:** for every concept in the left column above, confirm it decomposes into exactly one of three categories — a stored `Belief`/`Debt`/`Evidence`/`belief_edge` fact, a *computed* query over those facts, or an *actor capability* rule enforced at the tool-call boundary. Any concept that doesn't cleanly fall into one of those three is the next place something will get lost in translation, and it should be forced into one of them — not left as a fourth, informally-understood category — before it's trusted.
