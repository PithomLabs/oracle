Fair criticism. The last pass was a compliance check against my own findings — that's auditing, not adversary work. This time the attack starts from zero: assume the document is trying to fail conformance testing while looking conformant, and find where it succeeds. Brief calibration first: the spec survives several serious attacks — it does not smuggle a runtime, the mode/substitution semantics are behaviorally defined, and §12's failure-attribution discipline is genuinely hard to trip. Where it bleeds is below.

## Critical

**C1 — Fail-closed is relative to a self-authored contract, so the authority boundary is honor-bound.** §5.2 requires authorization evidence "defined by its integration contract." Who writes the integration contract? The integration author. An integration that declares zero required evidence for operation X is trivially conformant and produces uncontrolled external effects. The fail-closed mechanism is real, but it closes against a boundary the regulated component drew itself. The missing piece is an *objective* definition of "external effect" — e.g., a state change observable outside the requesting process — against which effect-capability is assessed, plus the obligation (deferred from v0.3, still missing) for each integration to declare its consequential operations and evidence requirements, with any discovered undeclared effect-capable behavior treated as a conformance-scope finding. Note the unifying damage: the spec's testability rests on declarations it never obligates. §16's "behavior matches the declared capability," §11's persistence-location inspection, and this all share the same missing foundation.

**C2 — Proposal–execution binding is unspecified; the substitution attack passes every invariant.** §5.3 has Solvent evaluate "the proposed consequential action." §5.2 has the Executor check "authorization evidence." §10 classifies the authorization reference as *correlation* — and §2 explicitly says correlation is not authority, not truth. Nowhere does the spec require that the authorization bind to the specific operation it covers, or that the effect-capable boundary verify executed-operation ≡ authorized-operation. So: Agent proposes X, Solvent authorizes X, client submits Y carrying X's evidence, Executor performs Y. Every invariant in §2 holds. All evidence is present and correlatable. §16's checks pass. The system just executed an unreviewed consequential action in perfect conformance. The denial→revision loop makes identity matter implicitly (revisions require new decisions), yet the spec never defines what makes two proposals the same proposal. Fix is vocabulary, not infrastructure: one new invariant — *authorization evidence binds the action it covers; the effect-capable boundary MUST reject execution where the executed operation does not correspond to the authorized one* — plus the binding semantics routed into the integration declaration from C1. This is the sharpest attack on the document and it lands cleanly.

**C3 — Conformance cannot test what Requirements demands, and the spec doesn't notice.** Requirements v0.3 §16 requires the suite to establish that "*invalid* authorization evidence prevents the corresponding external effect." But §5.3 makes Solvent's validity model opaque, and §16 scopes Solvent internals out. The harness therefore cannot distinguish valid from invalid evidence — it can only test the missing-evidence case — unless it controls a Solvent test double. Same problem for ambiguous-outcome distinctness (needs an Executor that emits ambiguity on cue), replay violations, and denial handling. Conformance for this architecture requires **deterministic fault-injecting stubs as first-class conformance actors**, and the actor model in §16 says nothing about them. Left unfixed, the suite silently degrades from the Requirements' assertions to a weaker set, and nobody will have decided that on purpose.

## High

**H1 — Denial is conflated with authority-unreachable, and the revision loop is unbounded.** §12 lists "authorization unavailable/unknown" as a failure with the same recovery sentence as everything else. But a Solvent timeout is not a denial: revising a proposal that was never evaluated is semantically wrong and trains agents to treat outage as rejection. Recovery needs a taxonomy: denial → revise/abandon; unavailability → retry/backoff/escalate; and these MUST NOT be interchangeable. Separately, §6's loop has no termination semantics — nothing bounds denial→revise cycles, nothing requires denial counts to be observable evidence, and in autonomous mode there is no human to notice an agent hammering the authority boundary indefinitely.

**H2 — Observability is asserted, not obligated.** §10 prefers "existing/native references"; §15 maps cross-role observation to "existing records/interfaces." Nothing requires those interfaces to expose the required references to a third-party harness. A deployment can be internally perfectly correlated and harness-blind — conformant by every stated rule, untestable in practice. The spec must state which it means: conforming components SHALL expose §10 references through a defined access mechanism, or v1 conformance is attestation-based and the Requirements' "observable and testable" claim gets downgraded explicitly. Same hole applies to the §4.1 discovery step — Scenario A's "work identified" evidence has no declared observation point.

**H3 — "Agent Skill" appears in §20 and it is the banned SDK wearing a coat.** The term is undefined, first appears in the closing deliverables list, and is derivable from nothing in the document — no scenario, no POC limitation, no Growth Gate record. Requirements §2 forbids a "workflow SDK"; a packaged client-side artifact of the cross-role contract is that thing unless explicitly scoped to declarations/documentation. Additionally, "Conformance Harness" is itself new infrastructure — defensible as test-only, but the spec should say the harness carries zero runtime obligations before someone ships §10's correlation identifier as a runtime injection feature.

## Medium

- **M1 — §4.4 SHOULD vs. §16 test.** "Ordinary work SHOULD proceed without Solvent" — then the conformance expectation "no unnecessary Solvent call" has no normative basis and can't be a pass/fail condition. Pick one.
- **M2 — Authority-validity model is unbounded.** Model 1 (§8) means authorize-once-execute-for-arbitrary-duration, with revocation semantics explicitly out of scope. The declaration obligation should include duration bounds or re-check schedules, and whether mid-flight revocation exists and who observes it.
- **M3 — Mode definitions are incoherent.** §13 lets "explicit policy" inject human gates into *autonomous* mode — which makes the modes indistinguishable in mechanism. Fix: mode = which boundaries' policy requires human action; autonomous = none, semi-autonomous = at least one. As written, Scenario C run in autonomous mode has undefined validity.
- **M4 — Negative invariants are untestable as phrased.** "Phases do not become persisted state" asks the harness to prove non-existence across systems it can't fully see. Reframe as a declaration-inspection test: among §11's declared persistence locations, none may be workflow-phase-authoritative — which again depends on the C1 declaration obligation.
- **M5 — Post-execution semantics are incoherent.** §7.7 allows human "reject" after execution — rejection of what, when the effect is permanent? Remediation of a produced effect is itself a consequential action subject to §5; the spec implies this and never states it, leaving "reject" ambiguous between domain-acceptance-rejection (meaningful) and effect-negation (impossible).
- **M6 — Human-modified proposals have no attribution model.** §7.3 lets a human "modify the proposal" before the authority boundary; if that happens out-of-band, the executed action's provenance is severed from the Agent's formulation. Human modification must flow through a boundary that versions the proposal and records attribution.
- **M7 — Concurrency and client-internal state are silent.** Two concurrent consequential proposals with interacting effects: ownership of interference (Solvent/Domain, presumably) is unstated. And a Temporal-wrapped client (§14) persists phase-like state internally — invariant 6 needs one line scoping client-internal persistence out, or Scenario D's "unchanged semantics" claim fights the obvious reading.

## Verdict

The architecture's *separation* logic survives adversarial reading; its *enforcement* and *testability* claims do not. C1 and C2 mean a motivated implementation can move consequential effects outside the authority boundary while passing every check the document defines — the spec is internally consistent and insecure, which is the worst state for a document whose entire purpose is enforcement. C3 means the Requirements' conformance assertions are not derivable from this spec as written. So §20's claim — "complete enough to derive" the Test Matrix, Harness, and Scenarios — is **false as stated**: those artifacts cannot be produced without inventing answers to C1–C3 and H1–H2, and whoever produces them first will make those decisions silently.

Routed actions, in order: (1) objective external-effect definition + mandatory integration declarations — this unblocks C1, M4, and half of C2; (2) proposal-execution binding invariant (C2); (3) fault-injecting conformance actors in §16 (C3); (4) recovery taxonomy and loop bounds (H1); (5) harness access obligation or explicit attestation downgrade (H2); (6) define or remove "Agent Skill" (H3). All are vocabulary and obligation statements — none require the infrastructure the spec rightly refuses to build.
