## High

**H1 — Operation-identity *comparison* semantics are undeclared; the binding chain's final link is unspecified.** §9.3 requires the same identity *definition* at proposal, authorization, and execution, and §18 requires the declaration to contain that definition. But a definition of identity content is not a definition of *equality*. Nothing requires the declaration to state the comparison rule — canonical serialization, declared equivalence relation, field-order sensitivity, type coercion. Attack: declaration defines identity as "target + operation + parameters"; Executor A compares canonical bytes, Executor B compares parsed structures with case-insensitive matching. The same proposal-authorization pair binds differently across executors — violating §20's substitution preservation directly ("exact operation/authorization binding" is on the MUST-preserve list), and reopening X≠Y in the false-accept direction. The §27 rejection of mandatory RFC 8785 is correct as a *mandate* rejection — but it leaves a hole the declaration content list must fill: the declaration MUST state its identity comparison rule, even a non-cryptographic one. The failure modes are asymmetric and both testable: bad comparison → false rejects (availability) or false accepts (security). Add to §18's required fields and to the substitution test set: *same identity, differing serialization → identical binding outcome*.

**H2 — The declaration obligation has no bearer for generic/third-party capabilities.** §5's Boundary Rule requires every ordinary-work tool to be declaration-covered; §8 requires every declared capability to have "an owned declaration." But the whole point of ordinary work is that invocation does *not* route through a checkable boundary — so no component is positioned to verify coverage at call time, and for generic capabilities (shell, web fetch, code execution — exactly the BM-IST research-agent toolset) there may be no distinct integration owner inside the deployment to hold the declaration. The MUST currently has no guaranteed subject. This is the same shape as criterion 12's earlier problem: the framework works wherever an owner happens to exist and silently doesn't where one doesn't. Fix is one line: *where a capability has no distinct integration owner, the deployment operator is the default declaration owner and bears the completeness obligation.* Without it, §26's Q1/Q2 hold only for owned integrations, and the Test Matrix will inherit a scope it can't enumerate.

## Medium
