I consolidated both reviews and filtered out recommendations that would re-expand the POC. The **pivot remains valid**, but the plan should be amended in a few important places.

The two reviews strongly agree that the direction is right: deployment separation has become confused with conceptual separation, and the POC's thesis does not require independent Coordinator/Conductor services.  

## Net-valid amendments

### 1. Make the pivot **reconnaissance-gated**, not predetermined

This is the strongest criticism.

The plan should say:

> Coordinator and Conductor are **provisionally** slated for collapse. Repository reconnaissance must determine which semantics are actually load-bearing. The pivot proceeds only if those semantics can be preserved in-process without weakening the thesis.

The complexity audit should classify every current pain point as:

```text
deployment complexity
API/integration complexity
inherent domain complexity
```

This prevents us from merely moving distributed complexity into a monolith. 

### 2. Preserve semantics, not components

The current Conductor feature list is too terse. Before replacing it, the plan must inventory the **actual semantics the POC uses**:

```text
task lifecycle
dependencies
blocked/ready behavior
cancellation
dead-end semantics
lineage / REOPEN
claim/release, if actually used
activity/history
```

Then explicitly classify each as:

```text
preserve
simplify
discard
```

This is more important than preserving Conductor itself. 

### 3. Preserve Solvent as the kernel, and make that boundary mechanically real

This is the most important architectural addition.

The reviews correctly identify that collapsing processes must **not** collapse authority boundaries.

The target rule should be:

```text
epistemic
  ↓
innermost kernel

must NOT import:
application
work
api
mcp
ui
domain-pack
```

Domain vocabulary must remain outside the generic epistemic kernel. 

Use a lightweight mechanical enforcement mechanism—import-direction checks or equivalent static CI validation. Do not rely solely on comments or architectural intent.

This is one place where the pivot actually makes the architecture **more important**, not less: Solvent is no longer protected by a process boundary, so the code boundary has to carry the meaning.

### 4. Keep agent and human authority explicitly separated

The reviewers are right that this becomes especially important when API, UI, MCP, and authority operations live in one process.

The plan must explicitly enforce:

```text
Agent:
    get_context
    submit_packet

Human:
    discharge
    promote
    retract
    reopen
    authorize
```

Agent requests must not be able to reach human consequential operations merely because everything shares the same HTTP server. Human attribution must come from authenticated server-side identity, never from a request-body `principal_id` or equivalent. 

I would add minimal CSRF/Origin/Host protection for browser-triggered consequential actions, but **not** introduce a full identity system.

### 5. Clarify the verifier model

The review correctly spots an ambiguity.

Use one verifier implementation:

```text
verifier package
      ↑
 ┌────┴─────┐
argus verify   ARGUS application
```

`argus verify` is the developer/reproduction entry point.

The application uses the **same library** when verification is needed.

No second verifier implementation and no file-based verifier-to-Coordinator handoff.

The review's proposed heavy additions—environment pinning, elaborate attestation, etc.—are not necessary for this POC. The important invariant is simply that verification artifacts are generated by the trusted verifier path and cannot be fabricated by agents. 

### 6. Keep the Domain Pack genuinely generic

The core should own the mechanism:

```text
beliefs
evidence
debt
edges
lifecycle
authority gates
```

The pack owns:

```text
claim vocabulary
evidence classes
retirement rules
falsifiers
domain verifier
domain-specific semantics
```

The evidence-class mechanism should remain generic and opaque to Solvent; do not hard-code new BM-IST concepts into the core merely because the verifier currently uses them. The review's principle here is valid even though some of its proposed specific evidence types are unnecessary for this POC. 

### 7. Add a real structural portability check

This is a good lightweight idea.

Don't implement a second real domain yet.

Instead, make CI prove that the core can compile against a **minimal/null domain-pack fixture**.

That demonstrates:

```text
core does not import BM-IST vocabulary
```

rather than merely asserting it in documentation.  

That is probably the cleanest evidence we can produce that the physics application is actually just the first domain.

### 8. Make the migration and test disposal explicit

The plan should state whether this is:

```text
in-place pivot
```

or a branch/new repo, and define rollback.

Also classify existing tests:

```text
PRESERVE — tests architectural invariants
REWRITE  — same behavior, new location
DELETE   — tests old service topology
ADD      — tests new boundaries
```

This is important because otherwise we will unconsciously preserve the old architecture through its test suite. 

### 9. Measure the simplification

The final plan should contain a concrete before/after ledger:

```text
processes
ports
databases
credentials
startup commands
internal HTTP calls
cross-process handoffs
```

The review's suggested measurements are exactly the right direction. 

The goal is not merely "cleaner code." We should be able to demonstrate that the POC actually became materially simpler.

---

## What I would **not** adopt from the reviews

Several recommendations are technically interesting but wrong for this pivot because they reintroduce complexity:

**Do not add container-per-agent isolation or image-hash provenance now.** That is infrastructure/security hardening beyond this POC.

**Do not introduce a new `PROPOSED/ACTIVE` edge state unless reconnaissance proves the current contradiction-edge model cannot preserve the required authority boundary.** The essential invariant is that agent-created edges are proposals and do not themselves cause retraction/promotion/authorization.

**Do not add elaborate verifier attestation, pre-registered script infrastructure, or environment fingerprints.** Keep the verifier deterministic and trusted, but don't turn the POC into a supply-chain-security project.

**Do not add another database or schema subsystem merely to preserve old service boundaries.** Inspect the current DB topology first and then make the smallest coherent organization.

**Do not turn the plan into another 18-section, 12-phase enterprise program.** The critique that the plan itself risks becoming over-engineered is valid.

# Consolidated architectural position

I would now lock the retrospective as:

```text
PIVOT: APPROVED, BUT RECONNAISSANCE-GATED

Preserve:
    Solvent epistemic kernel
    Domain Pack
    Verifier
    MCP boundary
    Human decision boundary
    Trust UI
    Work semantics required by the POC

Collapse:
    Coordinator service
    Conductor service
    Solvent HTTP boundary
    separate Trust UI process
    verifier artifact handoff
    internal service-to-service HTTP

Prove:
    authority remains separated from work
    agents remain below human authority
    domain pack is replaceable
    Solvent remains domain-agnostic
    deployment complexity materially decreases
```

The deepest valid point from the reviews is this:

> **The thesis is not “many services enforce separation.” The thesis is that authority, epistemic state, work, and execution remain structurally distinct.**

The pivot should therefore remove **deployment complexity without removing semantic boundaries**.

That is the version of the pivot I would now treat as the baseline.
